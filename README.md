# Домашняя работа «Микросервисы: принципы»

## Задание 1: API Gateway 

Для возможной реализации идеи API Gateway, я хочу предложить три варианта: haproxy, Traefik и kong.

**1. Haproxy**

Высокопроизводительный балансировщик нагрузки и reverse proxy. Отличный вариант для систем с большим количеством запросов. Поддерживает разные алгоритмы балансировки, проверку доступности серверов и гибкие правила маршрутизации.

Основной плюс: высокая производительность и контроль над распределением трафика.

**2. Traefik**

Reverse proxy и API Gateway, ориентированный на контейнерную инфраструктуру. Хорошо интегрируется с Docker и Kubernetes, умеет автоматически обнаруживать сервисы и обновлять маршруты. Также поддерживает автоматическое получение и обновление TLS-сертификатов через Let's Encrypt.

Основной плюс: удобно использовать в динамической инфраструктуре, где сервисы часто создаются, обновляются и удаляются.

**3. Kong**

Специализированный API Gateway с большим количеством плагинов. Поддерживает различные способы аутентификации, ограничение запросов, маршрутизацию и мониторинг. Подходит для централизованного управления API микросервисов.

Основной плюс: широкие возможности управления API и обеспечения безопасности.



### Сравнение программных решений

| Критерий | HAProxy | Traefik | Kong |
|---|---|---|---|
| Маршрутизация запросов | Да, через ACL и backend | Да, динамическая маршрутизация | Да, гибкая настройка маршрутов |
| Проверка аутентификации | Basic Auth, сложные схемы требуют доп. настройки | Basic Auth, ForwardAuth через внешний сервис | Basic Auth, JWT и другие плагины |
| HTTPS-терминация | Да | Да | Да |
| Балансировка нагрузки | Да, широкий выбор алгоритмов | Да | Да |
| Интеграция с Kubernetes | Возможна, требует настройки | Нативная, автоматическое обнаружение сервисов | Есть поддержка Kubernetes |
| Простота настройки | Средняя | Относительно простая | Средняя, зависит от используемых плагинов |


### Мой выбор:
Я выбираю Traefik. Т.к. в архитекторе микросервисов часто используют Kubernetes, Docker swarm, где сервисы могут постоянно масштабироваться и обновляться.
Почитав документацию, выяснил что Traefik умеет автоматически обнаруживать сервисы и обновлять конфигурации, без постоянного ручного вмешательства в конфигурацию. Также есть поддержка HTTPS и проверка аутентификации.

## Задание 2. Брокер сообщения

Для сравнения я возьму 4 ПО: RabbitMQ, Apache Kafka и ActiveMQ Artemis.


### Сравнение брокеров сообщений

| Критерий | RabbitMQ | Apache Kafka | ActiveMQ Artemis |
|---|---|---|---|
| Кластеризация | Да, поддерживает Quorum Queues | Да, репликация между брокерами | Да, кластеризация и HA |
| Хранение сообщений на диске | Да, при соответствующей настройке | Да, сообщения записываются в журнал | Да, поддерживает сохранение на диске |
| Производительность | Высокая | Очень высокая, особенно для потоковых данных | Высокая |
| Форматы сообщений | JSON, XML, Protobuf и другие | JSON, Avro, Protobuf и другие | JSON, XML и другие |
| Разграничение прав доступа | Да, через пользователей, vhost и права | Да, через ACL | Да, через роли и разрешения |
| Простота эксплуатации | Относительно простой, есть Web UI | Более сложный в настройке и обслуживании | Средняя сложность |

### Краткое описание решений

**1. RabbitMQ**

Брокер сообщений, который хорошо подходит для организации очередей задач между микросервисами. Поддерживает маршрутизацию сообщений, подтверждение обработки и отказоустойчивые очереди.

Плюсы:
- Удобный веб-интерфейс для мониторинга.
- Относительно простая настройка.
- Гибкая маршрутизация сообщений.
- Возможность сохранять сообщения при сбоях.

**2. Apache Kafka**

Распределённая платформа для обработки потоков событий. Хорошо подходит для систем, где нужно обрабатывать большой поток данных и сохранять историю сообщений.

Плюсы:
- Высокая пропускная способность.
- Хорошее горизонтальное масштабирование.
- Возможность повторного чтения сообщений.
- Подходит для аналитики, логирования и потоковой обработки.

**3. ActiveMQ Artemis**

Брокер сообщений с поддержкой нескольких протоколов, включая AMQP, MQTT и STOMP. Подходит для интеграции разных приложений и корпоративных систем.

Плюсы:
- Поддержка различных протоколов.
- Кластеризация и отказоустойчивость.
- Гибкая настройка безопасности.
- Поддержка постоянного хранения сообщений.

### Мой выбор

Я выбираю RabbitMQ.
Для микросервисной архитектуры он, мне кажется, наиболее удобный. RabbitMQ позволяет организовывать обмен собщениями между сервисами без необходимости ждать выполнения каждой задачи.
Есть удобный веб интерфейс, поддержка кластера и возможность хранить сообщения на диске.
Kafka тоже отличный вариант для масштабной потоковой обработки данных. Но я выбираю RabbitMQ т.к. выглядит хорошим компромиссом между производительностью, надёжностью и простотой эксплуатации.
